AI-Supported AICTE Approval Portal

A portal that takes an institution from application to decision with less paperwork and a clear status at every step. AI checks documents and infrastructure. Humans still approve.

The problem

AICTE approves technical institutions in India. Today that runs on manual, paper-heavy work across three stages:

  1. Application submissions
  2. Document verification
  3. Evaluation by multiple stakeholders

Result: delays, backlogs, high overhead, little visibility, weak security. Institutions cannot see where they stand. Evaluators get uneven load. Infrastructure claims are hard to check remotely.

Source of rules: the AICTE Approval Process Handbook. The portal already exists at aicte-india.org — this project is the AI layer over that workflow, not a rewrite of the entire regulator.

What we are making

One web app. Institution uploads an application. The system checks documents against APH norms, assigns evaluators, tracks status live, and uses the AR ruler (ARCore / WebXR) to verify physical infrastructure on site.

AI extracts, scores, and drafts. It never grants or rejects. Scrutiny, Expert Visit, and the Executive Committee still decide.

The six things in scope

These are the problem-statement items. Everything we implement now maps to one of them.

Feature What it means in the product
Application processing Intake, required-document list, state machine from draft → submitted → under review → decision.
Document verification OCR + field extraction from PDFs. Completeness check. Rules engine flags APH failures as deficiencies.
Evaluator matching Assign Scrutiny / Expert Visit members by expertise and current load, with conflict-of-interest blocked.
Real-time tracking Institution and evaluator dashboards: current stage, deficiencies, deadlines, feedback.
Analytics & reporting Counts by stage, time spent in each stage, evaluator load, common deficiency types.
Digital dimension tracking AR ruler in ar-ruler/: ARCore + WebXR hit-test on Android Chrome. Institution or EVC taps two real-world points; length / width / area are stored against the application.

Who uses it

RoleDoes
Institution Fills the application, uploads documents, sees status and deficiencies, replies.
Scrutiny Committee Reviews documents the AI already checked. Confirms or overrides findings.
Expert Visit Committee Checks infrastructure with the AR ruler (ARCore). Writes a visit report.
Executive Committee Sees the brief. Issues approval, deficiency letter, or rejection. Only this role decides.

Build this now

One vertical, not the whole handbook. Pick Increase in Intake for UG Engineering — it needs documents, scrutiny, and an infrastructure check, so all six features show up in one demo.

1. Application processing

  • Institution login and a single application form (programme, intake, campus facts).
  • Upload required documents. Block submit if the list is incomplete.
  • States: draft → submitted → scrutiny → deficiencies → evc → decision.

2. Document verification

  • OCR uploaded PDFs and extract the fields the form already asks for.
  • Rules engine (plain Python, unit-tested) for a small set of APH checks: faculty:student ratio, built-up area vs intake, required certificates present.
  • Each failed check becomes a deficiency with the clause cited and a plain-language reason.
  • LLM only writes the explanation from those rule results. It does not compute the numbers.

3. Evaluator matching

  • Mock panel of ~20 members with domain, load, and conflict flags.
  • Assign Scrutiny and EVC members by expertise + lowest current load. Same-institution / same-trust is forbidden.
  • Show the assignment on the committee console. Persist why that person was chosen.

4. Real-time tracking

  • Institution dashboard: current state, open deficiencies, next deadline, latest committee comment.
  • Committee console: assigned applications, structured report form, override with a reason.
  • Status updates without a page refresh (SSE is enough).

5. Analytics

  • One admin page: applications by state, average days in each state, load per evaluator, top deficiency types.
  • Numbers come from the same database as the workflow. No separate BI stack.

6. Digital dimension tracking

  • In progress: ar-ruler/ — ARCore via WebXR on Android Chrome. Not a camera overlay or OpenCV demo. Hit-test from the viewer ray; distance is Euclidean in ARCore world coordinates.
  • Institution or EVC measures a room; store length / width / area against the application. Nothing auto-fails — EVC still signs the visit report.

Stack for this prototype

FrontendNext.js + the existing Vite AR app in ar-ruler/
BackendFastAPI, one service
DatabasePostgres (applications, documents, checks, assignments, audit log)
IntegrityBlockchain: hash each workflow step (submit, check, assignment, decision) so the audit log is tamper-evident
FilesObject storage for PDFs and photos
AIOCR + a small LLM for extraction and explanations
ARARCore + WebXR in ar-ruler/ (Android Chrome)

Auth roles: institution, scrutiny, evc, ec, admin. Institution sees only its own applications. Mask Aadhaar / PAN / salary before any LLM call.

Niche: tamper-evident steps

Postgres remains the working database. After each workflow step (submit, rule check, assignment, AR measurement, committee action, EC decision) the portal hashes the record and anchors that hash on a blockchain. Officers can prove a row was not rewritten later. This is the integrity layer, not a replacement for Postgres.

Do not build yet

  • All 17 APH application types, new-institution, twinning, ODL.
  • Live DSC / emSigner, live land-records / fire-safety APIs, UGC / NBA / NAAC integrations.
  • Chatbot, speaking-order drafts, knowledge graphs, Kafka, IoT sensors.
  • Photo / video computer vision as a substitute for AR measurement.

If it is not in “Build this now,” it is later. Keep the demo one application type, one rules slice, one ARCore infra check, a step-hash on the audit trail, and a visible path from submit to EC decision.
