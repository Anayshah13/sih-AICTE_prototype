DJS_26_SW_06 · System Overview · v0.2 · APH-grounded

AI-Supported AICTE Approval Portal

A web application that walks an institution through an AICTE approval exactly as the Approval Process Handbook 2024–27 prescribes it: online application via the AICTE portal, deterministic norm checks, routed through the correct combination of Scrutiny, Expert Visit, Hearing, and Appellate committees, ending at the Executive Committee’s signed decision.

The AI does three things: it turns documents into structured data, it explains what the deterministic rules already decided, and it drafts speaking orders. It never decides.

Problem: DJSCE SIH 2026 · DJS_26_SW_06 Source of truth: APH 2024–27 Scope: hackathon prototype

1. Overview

Existing AICTE approvals are burdened by paper-heavy submissions, repeated deficiency cycles, sequential committee routing, and slow communication back to the institution. The portal already exists at aicte-india.org; this project is the AI layer over it, not a replacement.

Concretely: one FastAPI backend, one Next.js frontend, one Postgres database (with pgvector), one object store for PDFs and EVC videos, and four small AI microservices for OCR, computer vision, embeddings, and an LLM. Every claim the LLM makes must trace to a rules-engine result or an APH-handbook chunk.

3. Design principles

Principle 1 — The APH is the source of truth
Every rule the system enforces comes from a specific clause of the Approval Process Handbook 2024–27. The rule table is versioned by effective_from so an application submitted under APH 2024–25 is judged against 2024–25, even if 2025–26 is live.
Principle 2 — Rules decide compliance, LLMs explain it
Faculty ratios, built-up area, library titles, TER charges, security deposits, and eligibility windows are pure Python functions with unit tests. The LLM turns those results into deficiency briefs, speaking orders, and chatbot answers. It never computes the number.
Principle 3 — The Executive Committee signs
§1.10a and §2.25 name the Executive Committee (ratified by the Council) as the only body that can grant or reject approval. The system produces a decision brief for the EC and logs every override, matching the statutory shape of the AICTE Act, 1987.
Principle 4 — PII never reaches the LLM in raw form
Aadhaar and PAN seeding is mandated for faculty by §6.14i. Salaries are cross-checked via Electronic Clearing Service statements per §6.14a. All of these are masked before any LLM call; the model sees only hashes and buckets.
Principle 5 — Digital Signatures are enforced
§1.4.3 and Annexure-2 make DSC mandatory: “Institutions shall NOT be permitted to submit applications without DSC.” The system verifies every uploaded document’s signature at ingest and rejects unsigned submissions before they enter the workflow.

5. Actors & AICTE committees

The APH does not describe a single “officer.” It describes a routed committee process. The system’s role model reflects that.

Institution Registers via NSWS, pays TER, uploads DSC-signed documents, edits until final submission, fixes deficiencies, files appeal within 7 days. §1.4, §2.3, §1.11

Standing Appellate Committee (SAC) Hears appeals against EC decisions within 7 days of LoD/LoR. May recommend fresh SC/EVC. §1.11, §2.24

Both SC and EVC members are already picked via a “web-portal based automated selection process” (§1.8a, §1.9a). Our assignment layer improves the quality of that selection — it does not replace the statutory role of the committee.

12. APH rules engine

A rule is a pure function that takes an application snapshot and the norms in force at submission time, and returns a ComplianceCheck. Rules are unit-tested against APH worked examples. 

class ComplianceCheck(BaseModel):
    norm_key: str
    clause: str
    passed: bool
    actual: float | int | str | None
    required: float | int | str | None
    reason: str

def check_faculty_ratio(app: Application, norms: NormSet) -> ComplianceCheck:
    """
    APH 2024-27 §6.14 + Annexure-5.
    §6.12a(i) auto-reduction applies if admissions < 30% for 5 preceding years.
    """
    norm = norms.get("faculty_ratio", app.programme, app.level)
    required = norm.parameters["students_per_faculty"]

    faculty = app.data["regular_faculty_count"]
    adjunct = app.data.get("adjunct_and_pop_count", 0)
    cap = 0.15 if app.programme not in {"Design", "Planning"} else (
        0.20 if app.programme == "Design" else 0.30
    )
    counted_adjunct = min(adjunct, math.floor(faculty * cap / (1 - cap)))
    effective_faculty = faculty + counted_adjunct

    students = app.data["sanctioned_intake"]
    ratio = students / max(effective_faculty, 1)
    return ComplianceCheck(
        norm_key=norm.key,
        clause=norm.clause,
        passed=ratio <= required,
        actual=round(ratio, 2),
        required=required,
        reason=(
            f"{students} intake / {faculty} regular + "
            f"{counted_adjunct} counted adjunct = 1:{ratio:.1f}; "
            f"required 1:{required} per Annexure-5"
        ),
    )

Adding a rule is a Python function + a row in aph_norms + a unit test. There is no SPARQL, no OWL reasoner, no Jena.

What-if simulator (§2.6 hypotheticals)

The demo question — “what if we add 60 intake to UG Engineering?” — reuses the same engine: clone the application, patch sanctioned_intake += 60, re-run every rule, diff. This also validates §2.6a: “increase in intake demanded shall be approved in commensuration with equivalent infrastructure, facilities and faculty.”

14. LLM usage — where and how

The LLM does four jobs. It does not decide compliance.

JobInputOutput schema
Structured extraction OCR text + doc_type (e.g. Building Plan, Fire Safety Certificate, Bank Certificate) ExtractedFields: typed fields, per-field confidence, source-span pointer, PII masked.
Deficiency brief Failed compliance_checks rows DeficiencyBrief: one paragraph per failure in plain language, each citing clause. Suggests up to three path-forwards (§2.6a-c style).
Speaking Order draft Application + EC decision + citations SpeakingOrderDraft: header, background, clause-by-clause findings, precedents (from RAG), conclusion, appeal rights per §1.11.
APH chatbot (“AICTE digital assistant”, Ch. VIII item 13) Question + top-k aph_chunks + optional rules result AnswerWithCitations: answer text + list of clause_ref objects.
Grounding rule
Every factual claim in an LLM output must map to a tool result or an aph_chunk.clause_ref. If it cannot, the schema forces answer="I cannot verify this against the APH." The frontend renders that verbatim.

15. EVC video & infrastructure CV

§1.9f/g of the APH already prescribes the artefact: for an online EVC the institution produces a 30-minute video showing every infrastructural facility, uploaded to the Trust / Society YouTube channel with the URL shared on the portal. For a physical EVC, the institution records the entire proceedings with the same requirements. The video must show:

  • Entry and exit of the committee with timestamps.
  • Building Plan signed by the Scrutiny Committee.
  • GPS coordinates at the entrance of main building, academic building, administrative building, and library.
  • Class rooms, tutorial rooms, laboratories, workshops, drawing hall, computer centre, library, reading room, seminar hall, principal’s room, board room, common facilities.

This is exactly what the CV pipeline consumes:

  1. Ingest the YouTube URL, download the video to object storage.
  2. Sample one frame per second and de-duplicate detections across frames.
  3. Run YOLOv8 per frame; write per-frame infra_findings.
  4. Read overlaid GPS text with an OCR pass; compare against the Land Use Certificate / Building Plan coordinates.
  5. Aggregate counts (chairs, monitors, workstations, whiteboards) and compare against Annexure-3 / Annexure-4 requirements for the declared intake.
  6. Anything below a confidence threshold is queued for the EVC member, not auto-decided.
Honest limits
COCO-pretrained YOLO handles chairs, monitors, laptops, whiteboards but not lathes, spectrometers, or subject-specific lab equipment. v0 pilots the pipeline on classroom counts and generic equipment; fine-tuning is a v1 task. Do not overclaim in the demo.

16. Committee assignment

§1.8a and §1.9a already say SC and EVC members are chosen via a “web-portal based automated selection process.” Our layer replaces uniform random with constrained optimisation, keeping the process auditable.

Application complexity score

  • Number of approval categories in the same submission (§2.7c allows multiple).
  • New institution vs Extension vs Increase-in-Intake vs Merger.
  • Documents count & Annexure-1/2 completeness.
  • Prior deficiencies in the last 3 years.
  • Pending court cases (§1.11, §2.24).
  • Existing penal actions under Chapter VII.
  • Complaints on file with PGRC / SCSC.

Member reliability score

  • Past committee report quality (peer-reviewed by SHC).
  • Post-EVC outcomes (did the institution later fail? penalty).
  • Years of experience (capped at 20).
  • Domain expertise match (matches programme).
  • Historical throughput without incident.
  • Geographic proximity (for physical EVCs).

Constraints (hard)

  • Conflict of interest: no member from the same institution / trust; state-level exclusion per AICTE convention.
  • Load balancing: no member gets more than N EVCs per month.
  • Quorum: composition matches the committee’s statutory make-up.

Assignment: scipy.optimize.linear_sum_assignment (Hungarian) on a cost matrix built from complexity × reliability with the CoI and load constraints applied as forbidden edges. The chosen assignment and its cost are persisted in committee_assignments for audit.

Bias-mitigation
Reliability weights are objective, versioned, and displayed to the member. Members can appeal their score via the same PGRC/Ombudsperson flow §6.50 already prescribes for institutions.

17. Security, PII, DSC

  • PII masking at the OCR boundary. Aadhaar, PAN, phone, email replaced with stable salted hashes; salaries bucketed. The LLM never sees raw §6.14i / §6.14a data.
  • DSC enforcement. §1.4.3 and §2.3.4 make DSC mandatory. verify_dsc() runs at ingest; unsigned or invalid signatures are refused before entering the workflow.
  • Structured LLM outputs. Every LLM call uses response_format (Gemini) or an instructor-wrapped Pydantic schema. Free-form output on a required field is a validation error, not a soft warning.
  • Prompt-injection defence. OCR text is scanned for known instruction-shaped patterns before being sent to the LLM. Imperfect on its own; the real defence is that the LLM cannot approve or reject anything — only the EC can (§1.10a).
  • Row-level access. Institution scoped to its own institution_id. Committee members scoped to their assigned applications. Officer roles scoped by region.
  • Transport. HTTPS only. Documents served via short TTL signed URLs from object storage.
  • DPDP posture. Prototype demonstrates masking and consent capture. Production would need a DPO, retention policy, and a formal data-processing agreement with any hosted LLM vendor. Not claimed in v0.

18. Audit, appeal & override

audit_log is the accountability substrate.

  • Every state transition writes one row: {ts, actor, from_state, to_state, application_id, payload_sha256}.
  • Every tool invocation writes one row: {ts, actor, tool_name, args_hash, result_hash, duration_ms}.
  • Every DSC verification writes one row: {ts, document_id, signer_cn, chain_ok, revocation_checked_at}.
  • Every EC decision writes one row: {ts, ec_meeting_id, application_id, outcome, matched_recommendation: bool, override_reason?}.
  • Every SAC appeal writes one row: {ts, application_id, filed_within_window: bool, sac_recommendation, council_ratified_on}.
  • Rows are append-only; each includes prev_row_sha256 for tamper-evidence.
This replaces "blockchain anchor"
A Postgres hash chain, exported nightly to append-only object storage, gives the tamper-evidence property §7.13 wants. No public chain, no wallet, no foreign dependency. Consistent with the §6.14i data-sovereignty posture.
